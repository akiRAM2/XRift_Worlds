# VATの実装ノート

## 1. データと処理の分担

VATは「頂点IDとフレームから、GPUで位置・法線を復元する」方式です。CPU側ではフレームごとに頂点配列を更新せず、時刻のuniformを更新します。CPU負荷の削減と引き換えに、GPUメモリ、頂点テクスチャ読み込み、初期ダウンロードが必要です。

このサンプルのベイクはNode.jsとThree.jsで行います。BlenderやAlembicは必要ありません。他のDCCから移植する場合も、固定トポロジーと頂点の対応を維持する必要があります。

## 2. 球のVAT形式

| 項目 | 値 |
| --- | --- |
| 基準メッシュ | `SphereGeometry(1, 96, 64)` |
| 頂点数 | 6,305（UV継ぎ目・極の重複頂点を含む） |
| フレーム | 120 / 12秒ループ |
| 幅 | 1,024 texel |
| 1フレームの行数 | `ceil(6305 / 1024) = 7` |
| 高さ | `7 × 120 = 840` |
| 位置と法線 | それぞれRGBA16Fのrawバイナリ |
| 1テクスチャ | `1024 × 840 × 4 × 2 = 6,881,280 bytes` |
| 2モード・位置法線の合計 | 27,525,120 bytes（26.25 MiB） |

RGBにはローカル座標または法線XYZ、Aには1を格納します。未使用texelは0です。位置と法線は別ファイルです。rawデータに画像ヘッダーはありません。16bit floatを`Uint16Array`へ格納し、読み込み側は`HalfFloatType`として扱います。生成・実行は一般的なlittle-endian環境を前提とし、異なるエンディアンへの変換は実装していません。

頂点ID `i`、整数フレーム `f` のtexel中心は次です。

```text
x = i mod W
y = f × rows + floor(i / W)
u = (x + 0.5) / W
v = (y + 0.5) / H
```

`vatIndex`という専用属性を基準メッシュに付けます。インデックス付きメッシュでも、描画順や三角形番号ではなく属性の頂点IDを使います。

実行時のフレーム位置は `frame = (seconds mod 12) / 12 × 120`。`floor(frame)`と次フレームを取り出して`fract(frame)`で線形補間し、法線は補間後に正規化します。末尾の次フレームは0へ戻します。位置・法線を合わせて、球の頂点シェーダーでは4回のテクスチャ読み込みが発生します。影のパスも別途描画されます。

`World.tsx`の頂点数・行数・フレーム数とベイク側は一致させてください。metadataは形式の記録であり、現実装はこれを自動ロードして定数を変更しません。

## 3. ベイクと法線

FLOATは周期的なsin/cosを組み合わせた半径変化と伸縮です。SQUEEZEは球の中心を往復させ、棒の付近に滑らかな溝を作ります。溝は放物線と`tanh`で滑らかに制限し、接触時には周辺を膨らませます。厳密な体積保存や軟体物理ソルバーではありません。移動速度を接触付近で落とすことで、押し込まれて抜ける動きを表します。

表示上の棒の半径は0.35mです。ベイクでは半径0.39mを使用し、half float量子化や低解像度面のための余裕を設けています。変形後に平面ポリゴンが棒を横切らないかも確認します。

法線は基準球上の接線・従接線方向へ微小にずらした点を変形し、中央差分から接線を得て外積で計算します。位置だけを変形し元の法線を使うと、凹みのハイライトが整合しません。

同じ頂点数でも頂点の並べ替え、メッシュの最適化、統合、DCCでの再出力により対応が崩れることがあります。ベイクと再生で同じジオメトリを作るのが、このサンプルの対応維持方法です。

## 4. データテクスチャの注意

- 位置・法線には色変換を適用しません。Three.jsでは`NoColorSpace`、DCCではNon-Colorとして扱います。
- rawバイナリにはsRGBやガンマの情報がありません。画像形式へ変える場合は色変換による座標の破損に注意します。
- half floatは32bit floatよりメモリを抑えられますが、座標が大きいほど精度が粗くなります。遠いワールド座標を焼き込むよりローカル座標を使います。
- 球では`NearestFilter`、mipmapなしとし、フレーム補間をシェーダー内で明示します。隣の頂点やフレームの混入を避けます。
- CPUが持つテクスチャ配列、ダウンロードキャッシュ、GPUテクスチャの総メモリは、ファイル容量だけでは見積もれません。

## 5. PBR材質、マーブル、影

`MeshPhysicalMaterial.onBeforeCompile`で既存のライト計算を保ちつつ、`begin_vertex`と`beginnormal_vertex`を差し替えます。これはWebGLRenderer向けの実装です。WebGPURendererへ移行する場合はNode Material / TSLなどに書き直します。

流れるマーブルはVATに色を焼き込まず、基準球の3D座標をフラグメントシェーダーへ渡して計算します。sin/cosの歪み、6色の滑らかな補間、`fwidth`で境界を処理した細い白い帯で構成します。UVの継ぎ目を避けられ、形状が伸びても模様が表面と一緒に伸びます。60秒周期の座標回転・歪みにより模様自体も流れます。

球の影には`customDepthMaterial`を指定し、表示と同じ位置VATを読ませます。通常の深度材質のままでは基準球の影になります。今回のライトはspotlightです。point lightを追加するなら`customDistanceMaterial`側にも対応が必要です。

CPUのbounding sphereは変形前のメッシュからは決まりません。移動も含む保守的な半径10mを設定しています。レイキャスト、物理コライダーもGPU変形へ自動追従しません。この実装の球は視覚展示で、床と棒には固定コライダーがあります。

共有uniformは表示用材質と深度材質の両方へ渡します。シェーダーの構造を変える場合は`customProgramCacheKey`も適切に変更します。不要になったGeometry、Material、Textureは破棄します。

## 6. 草の差分VAT

草は7枚の葉を持つ1株をベイクし、同じデータを多数の株で共有します。各葉は4セグメント、9頂点なので、1株は63頂点です。

| データ | 形式・容量 |
| --- | --- |
| 位置差分 | 63 × 64 × RGBA16F = 32,256 bytes |
| 法線差分 | 同上 = 32,256 bytes |
| 基準メッシュ | 63 × 10 × Float32 = 2,520 bytes |
| 合計 | 67,032 bytes |

基準メッシュは頂点ごとに位置XYZ、法線XYZ、葉の幅方向のオフセットXYZ、高さ比を格納します。位置・法線VATは基準姿勢との差分です。ベイクでは根元ほど硬いばね関節を積分し、周期的な突風に対する穂先の遅れ・行き過ぎ・戻りを保存します。初期の過渡状態を避けるため12周期を計算し、最後の1周期を64フレームに記録します。

実行時には基準形だけを株のランダムなyawで回し、変位は風向きへ回します。両方を株のyawへ回すと、草の倒れる向きまでばらばらになります。法線も同じ座標変換を行い、基準法線と差分を足して正規化します。

時刻から風向きへの位置射影を引いて、株ごとに再生位相をずらします。

```text
phase ≈ seconds / gustPeriod − dot(origin, windDirection) / wavelength
```

この位相に低周波の歪みと株ごとの微差を加え、機械的な直線の波を避けます。曲がった先端を明るくする色補正で、遠方でも風の波を見せます。これは照明の厳密なシミュレーションではなく視覚的な強調です。

草ではY方向を`RepeatWrapping`とし、texel中心を参照します。現在は`magFilter=LinearFilter`、`minFilter=NearestFilter`です。拡大時のフレーム補間をハードウェアに任せていますが、縮小時も常に線形補間する設定ではありません。両者を変更する場合は葉同士の混入とちらつきを確認してください。

## 7. インスタンシング、LOD、時間

120m四方を12m角の100チャンクへ分割します。最大密度は12株/m²、1チャンク1,728株、全体172,800株です。各インスタンスはXZ位置・yaw・scaleの4値を持ち、草の変位データは共有します。

カメラからの距離でinstanceCountを減らし、描画する葉を7→4→2枚へ減らします。遠方の葉は幅を広げて見かけの密度を補います。チャンク境界の画質、draw call数、近距離の頂点数は端末ごとに確認が必要です。インスタンシングを使ってもGPU負荷がゼロになるわけではありません。

白い風の軌跡はVATではなく、時刻から経路を計算する半透明リボンです。`depthWrite=false`で草や他のリボンとの干渉を抑えます。空はカメラ位置に追従する内向きの球です。

草と軌跡の実行時時刻は96秒周期で折り返します。各時間成分をこの周期内の整数回の変化に揃え、折り返し時の不連続を避けながらfloatの精度低下を抑えます。球の形状は12秒、色は60秒で別に折り返します。

XRiftでは`useServerClock().now()`から位相を直接算出します。ローカルのdeltaを積算するより、途中参加や時刻補正から復帰しやすくなります。時計誤差の実測や、多人数での見え方の一致は別途検証が必要です。

## 8. XRift配信で確認した事項

### アセットURLとWindowsの区切り文字

`useXRift().baseUrl`には末尾の`/`があります。`${baseUrl}vat-position.bin`のように連結します。

確認したCLI 0.25.0同梱SDKでは、ファイル収集時の`path.relative`をそのままremotePathへ渡していました。Windowsではネストしたパスがバックスラッシュになり、ブラウザが要求するスラッシュのURLと一致せず404になる事例を確認しました。このサンプルはVATを`public/`直下へ置いて回避しています。将来のSDKで修正されている可能性があるため、永久的な仕様とは扱いません。

### CSSとCSP

`cssCodeSplit=false`では開発プレビューのCSSまでFederationのWorld entryへ関連づけられ、XRiftホストのCSPでアセットドメインからのstylesheet読み込みが拒否されました。`true`にするとWorldはCSS依存を持たず、プレビューCSSを分離できます。ホストのCSPを緩める必要はありません。

### 共有ライブラリ

FederationのReact、Three.js、R3Fなどはホストの実体を使います。狭い`requiredVersion`でホストの版を拒否すると同梱の共有チャンクへフォールバックし、そのファイルが配信対象から除外されている場合は読み込みに失敗します。この構成では`requiredVersion: '*'`と共有設定を使用しています。ただし、版の互換性を自動保証する設定ではないため、ホスト更新時は実際の描画を確認してください。

### アップロードと検証

アップロード成功直後も、審査反映まで以前の稼働バージョンが返ることがあります。稼働版・ACTIVE状態・公開範囲を確認し、実際のsceneUrlを基準に次を確認します。

1. entryと追加チャンクが取得できる。
2. VATの配信がHTTP 200で、バイト数とSHA-256がビルド済みファイルに一致する。
3. 不要なCSS依存がentryに含まれない。
4. 本番に入場し、表示・操作・コンソールを確認する。

ファイルのHTTP成功だけでは本番描画や端末性能の確認にはなりません。

### 照明

ワールドのライトは球以外にアバターも照らします。PBRの球の見た目だけで光量を決めると、アバターが白く飛ぶ・暗くなることがあります。環境光とスポットライトを調整し、必要に応じて展示物や床の材質側に弱い発光を足します。材質の発光は他の物体へ光を足しません。アバターと展示物の両方で確認します。

## 9. 検証の範囲と限界

`verify-passage.mjs`は全記録フレームの頂点と三角形の辺上のサンプル点を使って、棒との距離を検査します。NaN/Infinity、法線長、末尾→先頭を含むフレーム間の移動量も検査します。全三角形内部・フレーム間補間の連続衝突検出や、厳密な体積保存の証明ではありません。

草のベイクは地面より下への移動、最大変位、葉の中心線長の誤差、ループ端の差を出力します。これらはベイク品質の目安であり、すべてのGPUでの描画を保証しません。

実施済み: 生成スクリプト実行、通過形状チェック、型検査、ビルド、ブラウザ表示、XRift標準チェック、配信アセット取得。

公開用コピーの再現チェック（2026-11-02、Windows / Node.js 24.20.0）:

- lockfileから独立インストールし、`npm run bake`で7個のバイナリを再生成。すべて同梱データとSHA-256が一致。
- 通過形状: 棒との最小余裕0.02882m、最大フレーム間移動0.48655m、法線長0.99922〜1.00000。検査の合格基準を満たす。
- 草: 合計67,032 bytes、最小Y=-0.00590m、最大曲がり0.49675m、中心線長の最大相対誤差0.02745、ループ端の差の超過量約0.0000116m。根元の葉幅により僅かに地面下へ出る頂点があり、厳密に地面より上だけに制約したモデルではない。
- 固定した開発ツール依存には`npm audit`でmoderate 4件（`vite-plugin-dts`とその推移依存）が報告される。型定義生成ツールのメジャー更新はこのサンプルでは行っていない。

未実施・未実装: Questの負荷測定、各種端末のhalf float filtering互換性検証、全時間の連続衝突判定、実行時の任意障害物への対応、トポロジーが変わるVAT、point light用の影、GPU変形へ追従する球の物理コライダー。
